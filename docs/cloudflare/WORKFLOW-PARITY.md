# Profile and family review: upstream evidence and selected behavior

This evidence map compares the implemented member-profile review subset with the pinned ChurchApps sources. It records deliberate compatibility boundaries rather than claiming full DoingApi workflow parity. It does not cover account deletion, service-plan confirmations, general workflow cards, or external notifications.

Sources: API `5f9c1716e9180ba194c5cf0d96c0552abce9021b`; B1App `85c9e7d96b2f1659fd897191fb719095a176fa0f`; B1Admin `558c5ac74f2db7e7dab8d85e3c47dfee96446170`. For B1Admin, the original commit was read separately from the adaptation's modified working tree. License notices and repository scope are in [UPSTREAM.md](UPSTREAM.md).

## Request shapes

The web member form builds `data` as a JSON-encoded array, not an object keyed by field. See [ProfileEditPage.tsx, line 329](https://github.com/ChurchApps/B1App/blob/85c9e7d96b2f1659fd897191fb719095a176fa0f/src/app/%5BsdSlug%5D/mobile/components/screens/ProfileEditPage.tsx#L329):

```json
[
  { "field": "name.first", "label": "First Name", "value": "Morgan" },
  { "field": "contactInfo.mobilePhone", "label": "Mobile Phone", "value": "555-0102" },
  { "field": "familyMember", "label": "Add Family Member", "value": "{\"first\":\"Sam\",\"last\":\"Example\",\"prefix\":\"\",\"mobilePhone\":\"\",\"householdRole\":\"Child\"}" }
]
```

Known applied profile fields are `name.first/middle/last/prefix`, `photo`, `birthDate`, and `contactInfo.email/address1/address2/city/state/zip/homePhone/mobilePhone/workPhone`. `familyMember` creates a new person without an ID in the subject's household; it has no existing-relative target ID. B1Admin accepts both the newer JSON family object and a legacy plain first name ([RequestedChanges.tsx, line 22](https://github.com/ChurchApps/B1Admin/blob/558c5ac74f2db7e7dab8d85e3c47dfee96446170/src/serving/tasks/components/RequestedChanges.tsx#L22)).

The enclosing task includes `title`, `status`, `associatedWithType/Id/Label`, `createdByType/Id/Label`, optional `assignedToType/Id/Label`, and `data`. For member requests the API overwrites subject, creator identity and status, but accepts assignment fields from the request. The web form fills assignment only after successfully loading the configured group; its swallowed lookup error can leave the task unassigned ([ProfileEditPage.tsx, line 379](https://github.com/ChurchApps/B1App/blob/85c9e7d96b2f1659fd897191fb719095a176fa0f/src/app/%5BsdSlug%5D/mobile/components/screens/ProfileEditPage.tsx#L379)).

## Claims versus enforcement

1. **Approval selection is partly a frontend policy upstream.** The web form avoids direct own-profile writes when a group is configured, but the direct self-save endpoint does not enforce that setting. The family-add endpoint does enforce it. A port that enforces both server-side is deliberately stricter.
2. **Task visibility is not reviewer authority.** Assigned-group membership can allow viewing; applying another member's profile requires People.Edit, and closing the generic task requires Tasks.Edit. The inspected flow does not replace these permissions with a check that the actor belongs to the configured review group. The Apply button is rendered for an open directory-update task, even when subsequent API writes may be denied.
3. **Closed does not prove applied.** The review UI shows an “applied” status for `Closed`, but generic task editing can close a directory-update task without applying any person changes. No dedicated outcome, rejection reason, or decision endpoint exists for this task type in the inspected implementation. Account deletion has a separate decision endpoint; its existence does not extend to directory updates.
4. **Apply is not atomic or idempotent upstream.** The people save and task close are separate HTTP/database actions. If closing fails after saving people, a retry can add the same new family member again. Two reviewers can both apply an open request. The existing single-component `applying` flag and status check prevent only repeated clicks in that mounted browser state. TaskRepo's conditional assignment update is for serving assignments, not directory-update approval.
5. **Existing-relative edit authority is not implied by shared household membership.** Upstream permits reading one's household and adding a new family member under constrained conditions. It does not grant arbitrary writes to all existing household members. Adding that feature requires an explicit target/relationship policy and fresh checks at decision time.
6. **Stored changes require server validation.** Upstream's server task helper validates inline photos but retains arbitrary nonphoto change entries. The reviewer client has the field whitelist. The port should validate fields, types and lengths before storing and again before applying; subject/tenant/reviewer routing must come from trusted server state. Proposed household IDs, membership roles/status, account IDs and permission changes must not become authority.

## Implemented adaptation contract

The implementation lives in [member-approvals.ts](../../cloudflare/src/member-approvals.ts), [member-profile.ts](../../cloudflare/src/member-profile.ts), [migration 0023](../../cloudflare/migrations/0023_member_approvals.sql), and the protected-task paths in [tasks.ts](../../cloudflare/src/tasks.ts). Policy configuration uses [membership.ts](../../cloudflare/src/membership.ts) and [CloudflareChurchSettings.tsx](../../src/cloudflare/CloudflareChurchSettings.tsx). URLs below have the application's outer `/api` prefix omitted.

| Method and path | Selected contract |
| --- | --- |
| `GET /membership/churches/current` | Includes the current string `directoryApprovalGroupId`; an absent or explicit empty policy is returned as `""`. |
| `GET /membership/churches/directoryReviewGroups` | Global Settings Edit only; active current-tenant `{id,name}` choices, without requiring Groups View. More than 1,000 choices returns 413 rather than a truncated selector. |
| `POST /membership/churches` | One current-church array record with flat `directoryApprovalGroupId`; a trimmed empty string clears it. Optional name/time zone edits remain supported. Raw settings and public-host mutation are rejected. |
| `POST /member/v1/profile-requests` | `{kind:"profile"|"family-add"|"family-edit",changes:{...}}`; `personId` is required only for `family-edit` and forbidden for the other kinds. Creates a request and its My Work task together. Identical pending submissions return the existing request; conflicting pending changes require cancellation before resubmission. |
| `GET /member/v1/profile-requests/my` | Requester's own requests, newest first. Both authenticated user and person identities must match. |
| `GET /member/v1/profile-requests/review` | Pending requests for an authorized current reviewer, oldest first; an unauthorized reviewer receives an empty list. |
| `GET /member/v1/profile-requests/:id` | Request detail for its requester or a currently authorized reviewer. |
| `GET /member/v1/profile-requests/task/:taskId` | Same protected detail resolved from a My Work task ID. |
| `POST /member/v1/profile-requests/:id/approve` | Empty object `{}`; apply through the server-side transaction. Other request fields are rejected. |
| `POST /member/v1/profile-requests/:id/decline` | `{reason?:string}`; optional requester-visible reason is limited to 500 characters. Applies no proposed fields. |
| `DELETE /member/v1/profile-requests/:id` | Requester's own cancellation; applies no proposed fields. |

The two lists accept `limit` (1–100) and `offset` (0–10000). They return arrays by default; `paged=1` returns `{items,pagination:{limit,offset,count,hasMore,nextOffset,truncated}}`. Request DTOs contain `id`, `taskId`, `kind`, `status`, requester/target IDs and display names, proposed `changes`, timestamps, `reason`, and `canReview`. Status is `pending`, `approved`, `declined`, or `cancelled`; this is separate from the metadata task's Open/Closed status. Private baseline fields and comparison snapshots are not included in these DTOs or generic task responses.

The upstream `POST /doing/tasks?type=directoryUpdate` adapter is **not implemented** and still returns 501. The selected API uses a structured `changes` object, not the upstream JSON-string change array. Other suite clients must call the selected contract or gain an explicit adapter; the legacy submission path cannot be claimed as compatible.

The administrative **Church settings → Directory approval group** selector configures this selected flow. **No review group** permits direct own-profile edits and new family additions, while existing-relative proposals still require staff review. Policy saves preserve unrelated settings in their existing array/object representation and validate the chosen active group in the same tenant. Their atomic guard rechecks Settings Edit, live account/person/session, previous settings/name/time zone and the group's current active state. This intentionally replaces the generic upstream settings-array write with a narrow validated field.

## Intentional policy and behavior differences

* Own-profile edits and new-family additions require review whenever `directoryApprovalGroupId` is configured. Direct member writes enforce that rule server-side. With no configured group they use the existing direct member endpoints; trying to submit those two review kinds instead returns 409.
* Only an absent stored setting or an explicit empty string disables review. Configured `false`, `0`, `null`, other non-string values, malformed duplicate entries and unsupported top-level settings shapes fail closed. An invalid configured group also cannot downgrade the flow to direct editing. Malformed top-level settings require staff repair before policy configuration; valid array/object storage is preserved by the settings API.
* Existing-family editing is always a proposal, including churches without a review group. The target must currently be another nonremoved person in the requester's household. This extends upstream's add-only family UI without granting direct write authority over relatives. The household view exposes identity/role, not relatives' private baseline profile fields.
* The server derives request subject, creator, church and routing. A configured review group must be active in the same church. With no group, existing-family tasks are assigned to an active bootstrap administrator, while the dedicated review queue is available to staff with global People.Edit authority. Absence of an active administrator fails with 409; it does not leave an unassigned request.
* A reviewer needs current global `MembershipApi/People/Edit` or the bootstrap admin role. For a configured review group, the reviewer must additionally belong to that group, have global `DoingApi/Tasks/Edit`, or be a bootstrap admin. Group membership alone is insufficient. There is no prohibition on reviewing one's own proposal: an otherwise authorized staff member/admin may do so. Separation of duties is not claimed.
* `profile` and `family-edit` accept only `firstName`, `lastName`, `middleName`, `nickName`, `birthDate`, `mobilePhone`, `homePhone`, `address1`, `address2`, `city`, `state`, and `zip`. They cannot change email, photo, account links, consent, membership status, household membership/role, permissions or administrative fields. `family-add` separately accepts `first`, optional `last`/`mobilePhone`, and the new person's `householdRole` enum Head/Spouse/Child/Other; it creates no login or invitation and leaves directory sharing disabled.
* Approval applies changed fields, records the decision, closes the linked task and writes the audit record in one guarded D1 batch. The guards recheck reviewer/session authority, requester identity/status/household, target household/role/account links, relevant prior field values, unchanged request state, task state and current policy. Concurrent identical decisions are successful replays rather than a second application; conflicting terminal decisions return 409.
* A changed configured review group prevents approval with 409 and leaves the request pending/task open. A reviewer authorized under the current policy may decline it, or its requester may cancel and resubmit. A requester logging out alone does not invalidate an otherwise valid asynchronous staff approval; requester disablement or changed identity/household can invalidate it.
* Generic task writes cannot forge or modify `directoryUpdate` tasks, and generic task deletion cannot remove them. [TaskPage.tsx](../../src/serving/tasks/TaskPage.tsx) disables ordinary status/assignment editing for these records in Cloudflare mode and uses the shared [ProfileRequestReview.tsx](../../src/cloudflare/ProfileRequestReview.tsx) component. That component calls the dedicated server decision endpoint rather than issuing the old People-save followed by task-close sequence. No email, push, webhook or other notification is sent.

## Verification and remaining boundaries

The latest focused local workerd/D1 run passed **30/30**: **11 functional approval tests**, **7 independent approval-security tests**, **4 church-settings tests**, and **8 existing member-profile tests**. The implementation agent ran this combined check; the earlier upstream documentation audit inspected sources without running the upstream application. No upstream test run or new browser result is claimed here.

[member-approvals.test.mjs](../../cloudflare/test/member-approvals.test.mjs) covers identity pinning, private changes excluded from task responses, concurrent family approval creating one person, existing-family proposals, reviewer permission/routing rules, generic-task tamper prevention, decline/cancel outcomes, stale fields/account links/households/policy, duplicate submissions, pagination/tenant ownership, hidden-value guessing, strict malformed-policy handling, capacity and the field whitelist. [member-approvals-security.test.mjs](../../cloudflare/test/member-approvals-security.test.mjs) injects competing changes after preflight and before the transaction: revoked reviewer permissions/group membership; reviewer logout/expiry/removal/relinking; changed requester or target identity/household/fields; changed policy; and revoked submission authority. It checks rollback without orphan tasks, requests, audit rows or guards, and also tests that requester logout alone does not defeat authorized asynchronous review. [church-settings.test.mjs](../../cloudflare/test/church-settings.test.mjs) covers configuration field validation, array/object preservation, the Settings-only group selector, tenant/archived-group rejection, and queued authorization/session/settings/group changes.

These results support the selected local API behavior, not live Cloudflare production operation, full upstream workflow parity, or a new browser/device verification claim. Remaining compatibility boundaries include the legacy directory-update task adapter, general Doing workflows, profile photos, email/account identity changes, modifying existing household roles/membership, account-deletion workflows, and external notification delivery. Local operator-issued account recovery is a separate implemented feature described in [ACCOUNTS.md](ACCOUNTS.md). Test and browser evidence for the wider application belongs in the main milestone verification record.
