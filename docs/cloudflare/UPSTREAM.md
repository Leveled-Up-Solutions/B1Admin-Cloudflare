# Upstream audit and compatibility boundary

This audit describes the source inspected for the Cloudflare adaptation. The selected target includes people, groups, calendar, sermon archives, selected Serving/Plans and My Work flows, roles/audit, and a member-facing PWA/mobile web experience. Check-in and giving are explicitly excluded; native app-store delivery is not required. Their appearance in the baseline inventory below describes upstream only, not an implementation promise or roadmap. See [the portal and mobile audit](PORTAL-UPSTREAM.md) for the selected member-facing sources and [the implemented member portal](MEMBER-PORTAL.md) for its narrower runtime boundary.

This is not a claim that every upstream feature has been ported or runtime-tested. The implementation and its verification record must be assessed separately. The work uses synthetic development data; no church records were migrated and no production deployment, live payment, ad transmission, or external notification delivery is part of this milestone.

## Actual architecture

B1Admin is a React 19/Vite 8 application, with MUI, React Router, TanStack Query, and the shared AppHelper package. Its build creates static assets; its data, authorization, storage, notification, and payment behavior depends on APIs. The package scripts use Yarn Berry, despite older README instructions that mention npm.

The API is an Express/Inversify modular monolith. Controllers use module prefixes directly (`/membership`, `/content`, etc.); a host may add an outer `/api` prefix. `src/shared/infrastructure/KyselyPool.ts` constructs `MysqlDialect` instances with `mysql2` pools. `Environment.initializeDatabaseConnections` lists eight connection configurations. The README and health response still list only six modules and are stale relative to the source.

The [route inventory](upstream-routes.json) records 1,010 literal HTTP decorators in 151 controller files, with source file paths. It was generated by reading top-level `src/modules/*/controllers/*.ts` and extracting literal `@controller` and `@httpGet/Post/Put/Patch/Delete` decorators. It excludes dynamic routes, nested controller directories, MCP routes, health routes, and WebSocket actions. The count measures the upstream baseline, not port coverage.

There are seven module directories with Kysely schema/migration files: membership, attendance, content, giving, messaging, doing, and commons. Reporting is the eighth configured database namespace but has no independent `db/DatabaseTypes.ts` or migration directory in this checkout. Its `ReportRepo.run(moduleName, rawSql, parameters)` dispatches queries to the selected module's Kysely database; report definitions are JSON files read from disk. A D1 port must bundle/translate those reports or explicitly replace selected reports. Merely creating an empty eighth database does not port reporting. `bridge` coordinates modules and `mcp` exposes tools; neither adds an eighth/ninth domain schema.

## Wire contracts worth preserving

* `POST /membership/users/login` accepts `{email,password}` or `{jwt}`; it also has upstream MFA/auth-guid variants. Success returns `{user:{id,email,firstName,lastName,jwt},userChurches:[...]}`. Each user church has `church`, `person`, `groups`, `apis`, and a church `jwt`; each API entry has `keyName`, `permissions`, and `jwt`.
* `POST /membership/churches/select` accepts `churchId` or `subDomain` and returns one user-church object. Client API keys such as `MembershipApi`, `ContentApi`, and `GivingApi` are significant to AppHelper.
* Upstream JWTs carry user identity plus, for church/API tokens, `churchId`, `personId`, `permissions`, `groupIds`, `leaderGroupIds`, and optional `apiName`/`membershipStatus`. Flat permission strings are generated by `buildPermStrings`; changing their separators or empty-content-ID handling changes authorization behavior. Upstream also supports scoped `cak_` API keys and OAuth tokens.
* People JSON nests `name` and `contactInfo`, although its MySQL row is flattened. Many save endpoints accept arrays and return arrays; substituting a generic object CRUD shape breaks existing clients. Deleting a person is a soft removal upstream.
* WebSocket payloads are `{churchId,conversationId,action,data}`. The local socket server replies to an initial client message with `action:"socketId"`; subsequent delivery covers messages, notification, presence, reactions, and other actions. A tenant event feed does not by itself implement conversation authorization, connection registration, or those delivery semantics.
* File APIs use metadata plus file contents or an upload URL contract. `/content/files/postUrl` may return `{url,fields,key,method:"PUT",rawBody:true,headers}` for S3-compatible providers. Downloads must distinguish public files from restricted church files.

The Cloudflare adaptation may deliberately diverge, but every supported endpoint should be tested against its declared request/response contract. API-shape similarity does not make upstream JWTs, passwords, or live data automatically portable.

## Cloudflare conversion risks

**D1 requires a query/schema port.** MySQL-specific `BIT`, date/time conversions, `DATE_ADD`/`DATE_SUB`, `DATE_FORMAT`, `TIMESTAMPDIFF`, `CONCAT`, JSON expressions, collations, update joins, and duplicate-key errors appear in migrations/repositories. SQLite booleans, date strings, integer versus floating-point money, unique constraints, foreign keys, and tenant-scoped joins need explicit choices and tests. Module tables such as `settings` can collide when combining previously separate databases. Every read/write must derive tenant context from authenticated identity, including foreign-record references and public endpoints.

**Workflow assignment confirmation uses MySQL advisory locks.** `doing/repositories/TaskRepo.ts::withAssignmentLock` calls `GET_LOCK`/`RELEASE_LOCK` on a dedicated connection around multiple repository calls and network work. D1 has no equivalent connection-scoped lock. A future port of that workflow engine must use an appropriate Durable Object serialization boundary, atomic state transitions, and idempotency. The milestone's tenant realtime Durable Object is not that implementation. Scheduled workflow jobs that depend on those locks remain disabled. The separately implemented Serving assignment responses and self-signup capacity checks use D1 operations; those selected endpoints do not imply that the upstream workflow engine or fairness/rotation scheduler has been ported.

**Payment event deduplication is correctness-critical.** `giving/repositories/EventLogRepo.ts` recognizes MySQL `ER_DUP_ENTRY`/errno 1062; the `2026-06-14_eventlog_unique_providerid` migration makes `(churchId,providerId)` unique after normalizing empty IDs. The donate webhook claims a provider event before processing, then also checks transaction IDs to avoid duplicate donations across different event deliveries. A later D1 payment adapter must use SQLite conflict handling, durable processing/retry state, signed raw-body webhook validation, and concurrency/failure tests. Manual synthetic donation records do not establish payment-processing parity. Live payments remain disabled.

**R2 is a useful storage target, with access checks still required.** Upstream `S3CompatibleStorageProvider` already supports custom endpoints and presigned PUTs and explicitly mentions R2. However, its list operation returns an empty list and move throws; other code still uses local filesystem or AWS S3 helpers. The Worker port can use R2 bindings directly, but must preserve private/public access, content-type handling, tenant-prefixed keys, bounded uploads and deletion consistency. Upstream Commons has additional private review/download rules.

**Realtime and timers need new adapters.** Upstream runs local `ws` connections or API Gateway WebSockets, plus AWS scheduled Lambda tasks. The schedules include every-minute webhooks/scheduled notifications, half-hour reminders/email/escalations/retries, and daily workflow/maintenance/digest work. The Worker scheduled handler cleans expired sessions/auth attempts and stale pending/deleting R2 files, then records a retry-safe hourly `job_runs` marker. It does not activate upstream email, SMS, web push, webhook delivery, payment dunning, content synchronization, or automation schedules. Those external effects remain disabled here.

**AWS and Node assumptions are wider than the database.** SSM secrets, SES, S3, API Gateway management, CloudWatch, filesystem reports/templates, Express middleware and multipart handling all need replacement or deliberate omission. Provider integrations also include Stripe, PayPal, HubSpot/Mautic, Expo/web push, AI, geocoding, video/content services and storage OAuth. Do not enable them merely because their packages still exist in the upstream frontend dependency tree.

## Suite and future website boundary

`CommonEnvironmentHelper` has `REACT_APP_API_BASE`, `NEXT_PUBLIC_API_BASE`, and `EXPO_PUBLIC_API_BASE`, but applies the override only in its development initialization. Production/demo/staging initialization hardcodes ChurchApps hosts. B1Admin has a `selfhost` initializer that redirects core namespaces to its own origin. It still explicitly points Lessons/Ask to hosted services, and its import/export settings link can send a JWT to `transfer.b1.church`. AppHelper notification navigation includes a hardcoded `https://admin.b1.church` destination. Stock photo and demo avatar URLs also reference upstream hosts. The Cloudflare mode must prevent unintended upstream requests and token handoffs; other suite clients require their own configuration or patches.

This repository does not rebuild `pottershandsministries.org`. A separate website can consume the explicitly supported, tenant-scoped public content APIs and authenticated APIs after their contracts and CORS origins are configured. Public response shapes should expose published, intended-for-publication content only, without people/contact details, draft content, internal notes, or private files. The selected member portal/PWA needs its own end-to-end verification; source inspection of B1App does not establish parity. Full B1Mobile/FreeShow/Lessons/Commons interoperability, identity federation, OAuth/SSO/MFA recovery, webhook delivery, arbitrary reports, worship/serving workflows, and external provider integrations remain separate acceptance work unless individually implemented and verified in this port. Check-in and giving/payment gateways are excluded by the user's current scope, rather than unfinished requirements for this milestone.

## Verification of this audit

Verified by source inspection: pinned repository contents, direct ChurchApps package versions/licenses, eight configured namespaces versus seven migration/schema directories, route counts, the login/person/file/WebSocket contracts, specific MySQL-only operations, timer handlers, and hardcoded hosts. This audit did not start the upstream MySQL application, exercise provider accounts, or run upstream integrations; it makes no runtime compatibility claim for those systems.
