# Cloudflare frontend integration

Build with `yarn build:cloudflare` or `yarn vite build --mode cloudflare`. During development, `yarn vite --mode cloudflare` runs Vite on `127.0.0.1:3101`, proxying `/api` and WebSockets to the local Worker at `127.0.0.1:8787`. The built app and Worker API can also share the Wrangler origin.

The Cloudflare stage rewrites every ChurchApps API configuration to the installation's `/api/<module>` path, including unported Lessons, Ask and Commons services. Unavailable routes never fall back to the hosted ChurchApps deployment. It skips Sentry initialization, disables analytics, removes external Google Fonts links, and uses Stripe's side-effect-free module entry because the shared apphelper package imports donation components even on non-giving pages. Payment features are not reachable in this stage. A browser check verifies that supported navigation makes no external requests.

The admin sign-in keeps the upstream `LoginResponse` structure and `UserHelper` permission mapping. The development session remains in memory: reloading requires sign-in. Sign-out revokes the server session, clears the query cache and removes client API permissions. API 401 responses return the user to sign-in. The separate `/portal` member app has its own session and offline shell; see the member portal documentation.

The login page accepts a manually supplied invitation link. It reads the token into component memory, removes it from browser history, and previews/accepts it through POST request bodies. New accounts set a password; an existing account confirms its current password and enrolled MFA before linking. Both return to normal sign-in. Members with no staff permissions are handed directly to the member portal without mounting the administration context; members with staff grants retain administration access. Administration currently selects the first church. The member portal has an explicit multi-church chooser and clears the old church data when switching.

**My account** in administration and **My profile** in the member portal provide password changes and optional authenticator MFA. The frontend counts Unicode characters consistently with the API's 12–128-character policy. Password and factor changes revoke server sessions and clear the relevant client session. Backup codes are displayed once in a blocking acknowledgement dialog; enrollment secrets and codes remain in component memory. Both clients handle the MFA sign-in challenge. The portal's security forms use its explicitly supplied token and never fall back to an administration session. Offline local recovery uses a single-use link whose token is removed from the URL; no email, invitation delivery or public registration is enabled.

## UI reuse and deliberate divergence

- Original people and groups list/create components are retained. People columns/export, household grouping and supported advanced-search filters use the D1 API. Group-membership filters honor roster permissions and group scopes. AI search, saved lists, bulk operations and unported reports remain hidden. See [directory behavior](DIRECTORY.md).
- Person and group detail editors expose the implemented fields and group membership operations; household management reuses the original editor. Scoped role grants control group editing and roster access without granting global administration. The original detail pages eagerly load many unported forms, reports, messaging and check-in services, so this milestone uses smaller adapters for the supported operations.
- Calendars use a scoped adapter over normalized D1 calendars/events. Calendar/event CRUD, group associations, explicit time zones, bounded list/week views, all-day exclusive end dates and daily/weekly/monthly/yearly recurrence are implemented. Recurring events support individual changes, future splits, whole-series changes and restoration of skipped dates. Timed events are converted from the displayed IANA zone to UTC; nonexistent local times are rejected, and metadata-only edits preserve an existing repeated-hour instant. Curated calendars, resource booking and approval workflows remain unported. See [calendar contracts and limits](CALENDAR_SERMON_API.md).
- Original Serving, plan types, plans, positions, service order, print preview and manual My Work task pages are mounted. The print preview stays in the same tab to preserve the development session; website-logo settings are not loaded. Templates, content-provider authentication, automatic fill, digital signage, notification delivery, confirmation workflows, task notes/reminders and workflow automation controls are hidden where those services are unavailable. Publishing a plan does not send messages. Fair automatic rotation remains backlog.
- Original sermon, playlist, roles and audit pages are retained with Cloudflare adapters. See `frontend-sermons.md` for publication and R2 archive behavior.
- The shell lists only the selected modules and displays an explicit unavailable notice for unported routes. This is an administration port, not a rebuild of pottershandsministries.org.

## Browser verification

Build the app, then run the isolated browser check:

```sh
# Install a Playwright browser once if needed.
yarn playwright install chromium
yarn build:cloudflare
yarn test:cloudflare:browser
```

The runner creates fresh temporary D1/R2/Durable Object state for each batch of at most three spec files, applies migrations and synthetic seeds, serves the compiled app at `http://127.0.0.1:8790`, then stops its Worker. It leaves the shared development preview unchanged. Fresh state also keeps verification from exhausting the unchanged login rate limit. Explicit spec arguments run one isolated selection.

The Playwright config refuses non-loopback base URLs, so these tests cannot target a hosted production deployment. For a targeted check against an existing local preview, run `yarn playwright test --config cloudflare.playwright.config.ts`; `B1_TEST_BASE_URL` selects its loopback port. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` can select an existing Chrome executable. Tests remove their synthetic groups, events, roles, plans and files. Person deletion is a soft delete; household deletion only permits unused households. Account tests retain uniquely named accepted accounts because no destructive account-deletion API is exposed. The isolated runner's temporary state can be discarded after verification. The config does not use the upstream pretest/login setup.

The browser checks exercise directory and household operations, advanced search, group/member/leader editing, scoped permissions, join requests, explicit-time-zone calendar CRUD and recurrence, viewer restrictions, original plan position editing and print preview, original My Work close/reopen, custom-role lifecycle, and module navigation including the audit log. Separate specs cover manual account invitations, administration and member-portal password changes/session revocation, sermon/R2 lifecycle, and the member portal at a mobile viewport. They assert behavior against the local Worker and D1 rather than mocked API responses. The network-isolation check records external requests and API/JavaScript failures.

The first milestone passed **10/10 browser tests in 18.3 seconds** against the compiled Cloudflare app served by Wrangler after fresh local migrations and a synthetic seed. The follow-up expands this suite for the additional behavior above; final executed totals are recorded in [VERIFICATION.md](VERIFICATION.md). Builds report a large-bundle warning and an outdated Browserslist-data warning. No production service is used.

The fourth milestone adds calendar/sermon/playlist scope controls, protected profile/family review through the original My Work page and member portal, paged member collections, and native R2 media playback/download. Approval-policy configuration lives in Church Settings; reviewers need the documented People Edit authority and routing permission. Scope-only users receive minimal selectors and controls without broad directory access. These are selected, tested adaptations rather than full B1App parity; see [WORKFLOW-PARITY.md](WORKFLOW-PARITY.md) and the final [verification record](VERIFICATION.md) for exact evidence and limits.

The exact upstream source (`558c5ac74f2db7e7dab8d85e3c47dfee96446170`) and the same installed dependencies produced 54 TypeScript diagnostics. The first Cloudflare milestone reduced this to 53. The follow-up cleanup resolves the remaining inherited diagnostics: both `tsc -p tsconfig.app.json --noEmit` and `tsc -p tsconfig.node.json --noEmit` pass with the existing strict compiler settings. The node configuration also checks the Cloudflare Playwright configuration.

The fixes use explicit optional-value guards, correct local API interfaces for fields missing from the installed helpers package, and typed conversions where the website renderer expects absent parent IDs while the editor preserves API `null` values. No blanket `any`, ignored diagnostics or weakened compiler checks were introduced. The renderer conversion preserves nested content and leaves the original editor data unchanged; direct runtime checks cover those invariants. Existing attendance cards also now forward their declared click handler through `Surface`. Website, payment, attendance and other excluded upstream screens are typechecked but are not thereby claimed as working Cloudflare features.
