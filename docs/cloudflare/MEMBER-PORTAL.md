# Implemented member portal

`/portal` is a responsive member web app backed by the local Worker, D1 and R2. It is a deliberately narrow custom React shell, not a full port of ChurchApps B1App's Next.js interface or B1Mobile's native application. The admin application reuses selected original B1Admin screens. The pinned source comparison is in [PORTAL-UPSTREAM.md](PORTAL-UPSTREAM.md); the separate public church website is not included here.

## Run and sign in

Follow [RUNNING.md](RUNNING.md) to migrate/seed D1 and start the local Worker and Vite frontend, then open `http://127.0.0.1:3101/portal`. The synthetic member account is `member@example.test` / `LocalDemo2026!`. It is linked to the synthetic Alex Example person in the demo church. This account is separate from the demo administrator and cannot use staff routes merely by changing the URL.

The portal accepts the existing `/membership/users/login` response with `userChurches[].jwt`. It keeps its bearer token in memory and tab-scoped `sessionStorage`, never in a URL or persistent `localStorage`. Reloading the tab restores the session. Sign-out calls the Worker logout endpoint before clearing local member state; the backend revokes the session. A failed logout remains visible for retry. Successful login/logout audit actions are generated by the server.

Accounts linked to multiple churches choose a church after sign-in. No selected bearer is written to session storage until that choice is made; cancelling revokes the pending sign-in. The header's **Change church** action uses the authenticated selection endpoint. Switching clears the previous profile, household, lists, search and serving drafts before loading the new context. Reload retains only the selected church bearer. MFA-enabled accounts first receive a verification screen for an authenticator or recovery code; the password is cleared at that point and the challenge/code remain only in component memory.

## Available member functions

| Function | Implemented boundary |
| --- | --- |
| Profile | Read and edit own name, phone, postal address and birth date when the church has no directory approval group; edit own directory/email visibility preferences independently. Account email, login identity, membership status, household association and existing household roles remain immutable here. Change own password with the current password, revoking all sessions on success. |
| Household | Read names and roles in the current household; add a new family member to that same household when direct additions are allowed. New records are private by default and create no login, invitation or account link. Existing other-person records and household assignments cannot be edited through the portal. |
| Church context | List the signed-in account's existing active church/person links and select one through the existing authenticated church-selection contract. Each resulting bearer is church-scoped and shares the original revocable session. No church registration or implicit membership creation. |
| Directory | Search opted-in members by name; email appears only with separate consent. No addresses, birth dates, phone numbers or administrative people data. |
| Groups | List own groups and available open/request groups; join/leave open groups or submit, track and cancel approval requests. Group leaders and authorized administrators can review, approve or decline requests with an optional reason. Archived groups are excluded from discovery/new joining/approval. Group leaders must transfer leadership before leaving. Joining a community group does not grant ministry qualifications. Private group rosters are not exposed by the member API. |
| Calendar | Read allowed church and own-group event occurrences supplied by the member API; recurring series and exceptions expand after visibility checks. The default window is the next 90 days; `from`/`to` ISO timestamps support windows up to 366 days. Display times in the device timezone. No RSVP or calendar editing in this shell. |
| Sermons | List published public sermons; play supported direct audio/video URLs; explicitly load related archive files and play/download authorized R2 files. No draft or future-publication access through member URLs. |
| Serving | Show own upcoming published-plan assignments; accept/decline, self-sign up for available permitted positions, and add/remove unavailable dates. The backend enforces ownership, the position’s self-signup setting, capacity and date constraints. No rotation/fairness redesign or workflow automation. |

The current shell loads the first API page: up to 100 directory entries, own groups, available groups and sermons, plus 200 calendar occurrences in the default 90-day window. Directory search filters that loaded page. The API supports bounded pagination for these lists, but the portal has no page or date-range controls yet. Archive attachment lists are capped at 100 files per sermon. These limits need client pagination work before larger collections are fully browsable.

The member contract is `/api/member/v1`: `me`, `household`, `churches`, `directory`, `groups`, `groups/available`, `calendar`, `sermons`, `sermons/:id/files` and `files/:id/download`. Profile writes use `POST me` with a flat whitelist: `firstName`, `lastName`, `middleName`, `nickName`, `mobilePhone`, `homePhone`, `address1`, `address2`, `city`, `state`, `zip`, `birthDate`, `directoryVisible`, `shareEmail`. Birth dates accept a real, non-future `YYYY-MM-DD` or null. `POST household/members` accepts `first`, optional `last`, `mobilePhone`, and `householdRole` (`Head`, `Spouse`, `Child`, `Other`). The server chooses the person ID, church and household. `GET churches` exposes only church ID/name/subdomain, linked person name/ID and the selected flag; switching uses `POST /api/membership/churches/select` with `{churchId}` and returns the existing suite user-church/JWT shape. Group mutations use `POST groups/:id/join` and `DELETE groups/:id/leave`. Serving calls reuse the selected `/api/doing` contracts: `assignments/my/upcoming`, assignment `accept`/`decline`, `plans/public/signup/:churchId`, `assignments/signup`, and `blockoutDates`. The browser never chooses another member's person ID for these self-service operations.

The selected profile/household behavior follows pinned B1App `ProfileEditPage.tsx` and API `PersonController.ts` (`save`, `addFamilyMember`, `getHouseholdMembers`). Upstream permits own-person edits with Edit Self, preserving administrative fields; household membership reassignment and editing another existing person require People Edit. The family-add endpoint does not impose a Head/Spouse gate, so this port does not invent one. Its new person is always filed in the caller's current household, with no account creation or association by email. Household reads return names/roles only, not other members' contact details or dates of birth.

Upstream B1App checks `directoryApprovalGroupId` and submits a Doing directory-update task when review is required. That approval-task workflow is not yet ported: the profile response explicitly reports `settings.profileEditMode: "staff"`, family additions are disabled, and direct personal-data writes return 409 with a staff-contact message. Consent changes remain available. The server rechecks policy, account link, current household, active person and current session/version inside the D1 mutation statement. Household additions are limited to 100 active people per household. No household is automatically created when a member lacks one. New additions are separate submissions; the client should refresh after an ambiguous network failure before retrying.

A separate synthetic account, `multi-member@example.test` / `LocalDemo2026!`, is linked to `church-demo` and `church-other`, with independent private people and household fixtures. The original `member@example.test` account remains single-church for existing examples.

Group requests preserve the upstream `/api/membership/groupjoinrequests` contract: object POST `{groupId,message?}`, GET `/my`, GET `/group/:groupId`, GET `/pending`, POST `/:id/approve`, POST `/:id/decline` with `{declineReason?}`, and DELETE `/:id` to cancel. Status values are `pending`, `approved`, `declined`, and `cancelled`. The additional `/api/member/v1/group-requests/review` lists only groups the caller currently leads or has a scoped Group Members Edit grant for; church-wide `/pending` requires a global grant. Original B1Admin `PendingJoinRequests` cards and decline dialog are reused on the admin group page.

The server binds the requester to the signed-in person and validates all tenant references. Reviewers receive the requester's name and request message, not their withheld directory email or phone. A partial unique index allows only one pending request per person/group; approval, membership creation and audit evidence commit in one D1 batch. Repeating the same decision is idempotent, conflicting terminal decisions return 409, and replaying approval after a later leave does not recreate membership. Closed/archived groups and removed people cannot be approved. These are deliberate strengthening changes from the source implementation. No notifications, email, webhooks, task-workflow events or automatic account creation are triggered.

Archive downloads send the bearer token in a fetch header and use `cache: "no-store"`. The portal creates a temporary blob URL for native browser playback/download and revokes it when replaced or unmounted. No token is appended to a media URL. The portal's playback/download cap is 25 MiB, checked against file metadata before downloading and against response length before buffering. This buffers the authorized file before playback and is not a large-media streaming solution; the API's larger resumable uploads and range responses do not imply browser-native authenticated seeking in this shell. Direct external media URLs contact their configured provider when played; the seeded/test media is entirely synthetic and local.

## Installation and offline behavior

The manifest provides a standalone `/portal` app entry and local SVG icon. A supported browser's `beforeinstallprompt` shows an Install button; otherwise the UI provides browser-menu guidance and accurate Safari Share → Add to Home Screen instructions. The service worker is registered only for production frontend builds, with `/portal` scope.

Only the public offline message and local icon are cached. Authenticated HTML, APIs, member records, bearer tokens and media are never put into the service-worker cache. An offline portal navigation displays a reconnect message; directory, sermons and serving require a connection. There is no offline private-data mode, push notification setup or app-store submission. Installation on physical iOS/Android devices remains unverified; a desktop mobile viewport test does not establish device installation parity.

## Original roles and audit screens

The admin shell mounts the original B1Admin Roles/Role and AuditLog pages. Cloudflare guards hide unsupported Everyone-role editing, predefined templates containing excluded modules, and editing another user's credentials. Adding a role member selects a person who already has exactly one local church account. When a selected person needs an account, a bootstrap administrator can create and copy a one-time local setup link; no email is sent. The original person selector remains in use. The selected custom role is granted only when the recipient accepts, and an existing active account must prove its current password and an enrolled factor when MFA is enabled. An administrator cannot reset that account through an invitation. Setup URLs remain in component memory and are not stored in browser storage. The bootstrap Domain Admins role is protected in both UI and API. The audit UI uses server-owned action metadata; where before/after snapshots are not implemented, `details` is `{}` rather than fabricated change data.

The original role permission checkboxes now match the complete API/content/action/scope tuple. The Cloudflare scope selector defaults to church-wide grants. A selected group can expose Groups and Group Members permissions for that exact group and Tasks permissions for work assigned to it; a ministry group can also expose Plans permissions for that ministry. The selector shows only scope kinds the current administrator may delegate. Global and scoped grants remain independent, and removing a scoped grant does not remove its global counterpart. A global grant still authorizes that action throughout the church even while viewing a narrower scope. Ministry membership alone grants no plan editing authority in Cloudflare mode.

## Verification boundary

The repeatable browser test is `tests/cloudflare/member-portal.spec.ts`. Against the running local Worker/Vite servers it creates isolated synthetic group and serving records plus a one-second WAV file in local R2, then verifies mobile-viewport login, directory search, group join/leave, assignment acceptance, self-signup, authenticated audio decoding, reload, logout and cleared session storage. It checks no horizontal overflow, JavaScript errors, failed API responses or external requests and removes its temporary records. The focused run passed on 2026-11-05 in headless Chrome at 390×844. Separate manual local-browser checks also exercised profile save/restore and unavailable-date creation/removal.

`cloudflare/test/portal-offline.test.mjs` verifies static shell cache policy, that API/media requests are not intercepted, and that the navigation fallback is limited to `/portal`. `cloudflare/test/maintenance.test.mjs` exercises the real scheduled handler through Miniflare, including expired versus valid auth records and repeated hourly markers. R2 stale-file cleanup is tested in `sermons.test.mjs`; realtime and member authorization have separate Worker integration tests. The repository-wide verification report records the final full-suite/build results.

`cloudflare/test/group-requests.test.mjs` adds seven real-D1 cases for concurrent duplicate submissions, tenant/ownership checks, live leader removal, scoped grants/revocation, concurrent approval/decline, cancellation/re-requesting, no membership resurrection, and archived/removed-record rejection. Those seven and the eight member integration cases passed, including member recurrence privacy, exceptions and pagination. `tests/cloudflare/group-requests.spec.ts` exercises the mobile member flow and original admin review UI; `account-issuance.spec.ts` exercises the original role-member selector and manual link creation. Consult the final verification report for browser run results.

Focused local Chrome runs passed the group-request browser workflow (1/1), existing member portal/media workflow (1/1), and original role scope/manual invitation workflow (1/1). The latter checks that scope toggling/deletion preserves the separate global grant, that invitation issuance does not yet add a role member, and that no invitation/email/notification API write or external request occurs. Original review avatars use the local upstream fallback so relative file paths are not misinterpreted as protected ContentApi URLs.

Remaining member scope includes upstream open registration, directory-change approval tasks, editing existing other household members or household assignments, list pagination/date-range controls, group conversations, notification preferences/push, full B1App navigation and video-provider embeds. These are explicit compatibility gaps. Check-in, giving and native-store delivery are excluded by the current request.

Milestone 3 focused tests in `cloudflare/test/member-profile.test.mjs` cover two-church listing/selection and household separation, profile validation and immutable identity, private family additions without accounts, both stored approval-setting shapes, the household-size cap, and policy/household/removal/account-link/session changes injected after the initial read but before the real D1 mutation batch. A queued-operation regression checks natural session expiry at D1 execution time for profile writes, family additions and household reads, with no data or audit changes after expiry. The focused suite passed 8/8 locally; the repository-wide verification report records the final coordinated results.

`tests/cloudflare/member-profile.spec.ts` covers the mobile church chooser, own personal/contact/date saves, directory consent, private family addition, household field projection, switching to a second church and reloading that context. It restores the synthetic profile and removes its added person afterward. The profile page keeps account email separate from the person's contact email and never submits account identity, household IDs or another existing person's ID. The staff-review mode disables direct personal-data editing but leaves consent controls available; it does not simulate an approval queue. The focused compiled-app run passed; consult the verification report for the final full-suite result.
